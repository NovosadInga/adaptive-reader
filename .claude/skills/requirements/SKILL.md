# Формулювання вимоги

Мета — домовитися, що саме робимо, до написання коду. Нечітка вимога коштує
переробки, а переробка з темпом «щодня по трохи» коштує тижнів.

## Спершу перевірити

- `docs/REQUIREMENTS.md` — можливо, вимога вже є або суперечить наявній;
- `docs/DECISIONS.md` — якщо вимога суперечить рішенню, сказати прямо й назвати його номер;
- чи наближає вимога до критерію успіху MVP («прочитати книгу цілком»). Якщо ні —
  сказати про це: можливо, їй місце після MVP.

## Чотири питання

Вимога сформульована, коли є відповідь на всі чотири.

### 1. Сценарій

Що робить читач і що бачить у відповідь. Конкретними діями, а не
«система підтримує X».

### 2. Краєві випадки

Що буде, коли: даних немає; запит не вдався; мережа зникла; файл пошкоджений;
дані неочікуваного вигляду.

Для AI-функцій завжди питати окремо: **що робимо, коли модель поверне не те,
чого ми очікуємо.** Це не рідкісний випадок, а звичайний режим роботи.

### 3. Критерій готовності

Як перевірити, що зроблено. Має бути перевірним:
«зберегла три цитати, перезапустила, усі три на місці», а не «працює добре».

### 4. Що це НЕ включає

Явна межа, щоб вимога не розповзалася. Найважливіший пункт для проєкту,
головна ціль якого — бути завершеним (D13).

## Правила

- Не вигадувати вимоги за автора. Незрозуміле — питати.
- Записувати результат у `docs/REQUIREMENTS.md`, показавши текст перед записом.
