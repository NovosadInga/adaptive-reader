# AI Adaptive English Reader

Персональна читалка англомовних книг із контекстною AI-допомогою.
Публічний портфоліо-проєкт.

## Перед роботою

Прочитай `docs/CURRENT_STATE.md` — там актуальна стадія й наступний крок.
Конкретні задачі — у GitHub Issues (D22), а не в документах:
`gh issue list --milestone "Phase 1 — Vertical slice" --limit 50`
(без `--limit` показуються лише 30 записів із 36).
За потреби: `docs/PROJECT.md` (vision), `docs/REQUIREMENTS.md` (вимоги),
`docs/DECISIONS.md` (рішення та їхня ціна).

Якщо не пам'ятаєш, як влаштована ця система — `docs/README.md`: що де лежить,
що означають коди `R`/`D`/`O`, як влаштовані issues.

PDF-блупринт у корені — історичний оригінал ідеї. Там, де він розходиться з
документами в `docs/`, правильні документи.

## Головне про продукт

Ядро — не переклад книг, а одна взаємодія: **виділив слово → побачив переклад
речення з підсвіченою відповідністю → читаєш далі.** Усе інше вторинне.

Автоматичне виділення складних місць — другорядна функція, і вона свідомо не
блокує головну (D3).

## Правила роботи

- Дотримуйся рішень із `DECISIONS.md`. Якщо якесь рішення заважає — скажи прямо
  й запропонуй його переглянути, а не обходь мовчки.
- Пояснюй архітектурні вибори й trade-offs, а не лише пиши код. Автор вивчає
  розробку AI-застосунків — це мета проєкту не менша за сам продукт.
- Найпростіше доречне рішення. Без зайвого рефакторингу й нових залежностей
  без причини.
- Mobile-first за замовчуванням.
- Не стверджуй, що працює, поки не перевірив. Кажи, що саме перевірив.

## Безпека

Репозиторій публічний. Ключі API — тільки через змінні середовища, тільки на
сервері. Ніколи не в клієнтському коді, ніколи не в комітах.

## Skills

- `/end-session` — наприкінці роботи. Нагадувати про нього, коли робота дійшла
  до логічної точки, але не запускати самостійно: тільки автор знає, коли сесія
  завершується.
- `/requirements` — коли з'явилася нова вимога. Пропонувати перед тим, як писати
  код, але не нав'язувати: іноді це справді дрібниця.

Питати автора, а не вирішувати мовчки. Краще зайвий раз запропонувати, ніж
зробити не те.

## Git

Прямих комітів у `main` немає (D21). Кожна задача — окрема коротка гілка
(`backend/…`, `frontend/…`, `docs/…`), злиття тільки через pull request.
У PR і в комітах посилатися на issue (`Closes #7`), щоб борд оновлювався сам.

Назви pull request і комітів починаються з префікса області:

```
backend/EPUB parser producing the shared book representation
docs/Record decisions D17-D21
frontend/Chapter view and navigation
```

Префікс описує **саму зміну, а не гілку**: коміт, що лежить у гілці
`backend/…`, але змінює лише документацію, має префікс `docs/`. Якщо зміна
зачіпає і код, і документацію — префікс за головною з них, але краще
розділити на два коміти.

**Один pull request — одна тема.** У PR є тільки те, що стосується
заявленого в його назві. Документація не їде разом із бекендом, друга задача —
разом із першою. Побічна правка, помічена по дорозі (застарілий README,
помилка в іншому документі, рефакторинг поруч), — не в цю гілку: сказати про
неї автору й запропонувати окрему гілку або відкласти. Перед `gh pr create`
перевіряти diff на сторонні зміни так само, як на секрети. Виняток —
документація, яку **вимагає** сама зміна: нове рішення в `DECISIONS.md`
або правило в `CLAUDE.md` для щойно доданого процесу йдуть у той самий PR,
окремим комітом із префіксом `docs/`.

Мова комітів, PR і всього в проєкті — англійська, репозиторій публічний.
Спілкування з автором у чаті — українською.

## Наприкінці сесії

Оновлюй `docs/CURRENT_STATE.md`. Нові важливі рішення дописуй у `docs/DECISIONS.md`
у форматі: рішення → чому → чим платимо.

Робочі сесії короткі й часті, контекст між ними не зберігається — документація
є єдиним способом не переказувати вже вирішене щоразу заново.
