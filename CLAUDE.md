# AI Adaptive English Reader

Персональна читалка англомовних книг із контекстною AI-допомогою.
Публічний портфоліо-проєкт.

## Перед роботою

Прочитай `docs/CURRENT_STATE.md` — актуальна стадія й наступний крок.
Задачі — у GitHub Issues (D22), не в документах:
`gh issue list --milestone "Phase 1 — Vertical slice" --limit 50`
(без `--limit` показуються лише перші 30 записів).
За потреби: `docs/PROJECT.md` (vision), `docs/REQUIREMENTS.md` (вимоги),
`docs/DECISIONS.md` (рішення та їхня ціна), `docs/README.md` (що де лежить,
коди `R`/`D`/`O`, як влаштовані issues).
PDF-блупринт у корені — історичний оригінал; де він розходиться з `docs/`,
правильні документи.

## Головне про продукт

Ядро — не переклад книг, а одна взаємодія: **виділив слово → побачив переклад
речення з підсвіченою відповідністю → читаєш далі.** Усе інше вторинне.

Автоматичне виділення складних місць — другорядна функція, і вона свідомо не
блокує головну (D3).

## Правила роботи

- Дотримуйся рішень із `DECISIONS.md`. Якщо якесь рішення заважає — скажи прямо
  й запропонуй його переглянути, а не обходь мовчки.
- Пояснюй архітектурні вибори й trade-offs, а не лише пиши код. Автор вивчає
  розробку AI-застосунків — це мета проєкту не менша за сам продукт.
- Mobile-first за замовчуванням.

## Безпека

IMPORTANT: репозиторій публічний. Ключі API — тільки через змінні середовища
на сервері; ніколи в клієнтському коді, ніколи в комітах. Секрети для GitHub
заводить автор вручну.

IMPORTANT: залежності — головний реальний ризик, бо чужий пакет виконується на
машині автора при `npm install`. Кожен новий пакет: поширений (десятки тисяч
завантажень на тиждень, живий реліз), із поясненням у PR, що він робить і чому
саме він; без `postinstall`-скриптів без пояснення; `npm audit` перед PR.

## Рев'ю (D28)

Код пише AI-агент, тому кожна зміна проходить незалежну перевірку, а авторка
розуміє її цілком до злиття:

- Перед `gh pr create` — `/review-pr`; висновок показувати дослівно.
- Опис PR за `.github/pull_request_template.md`, зокрема сценарій ручної
  перевірки «запусти це — побачиш те».
- Після відкриття PR його коментує Claude Code Review на GitHub. Жоден
  рев'ювер не блокує злиття — рішення завжди за авторкою.
- Нові технології пояснювати з основ, повністю, а не спрощувати.

## Skills

- `/end-session` — наприкінці роботи. Нагадувати, коли робота дійшла до
  логічної точки, але не запускати самостійно.
- `/requirements` — коли з'явилася нова вимога. Пропонувати перед кодом, не
  нав'язувати.
- `/review-pr` — перед кожним pull request, без винятків для малих змін.

Питати автора, а не вирішувати мовчки. Краще зайвий раз запропонувати, ніж
зробити не те.

## Git

Прямих комітів у `main` немає (D21). Кожна задача — окрема коротка гілка
(`backend/…`, `frontend/…`, `docs/…`), злиття тільки через pull request.
У PR і комітах посилатися на issue (`Closes #7`).

Назви PR і комітів починаються з префікса області, який описує **саму зміну,
а не гілку** (D24):

```
backend/EPUB parser producing the shared book representation
docs/Record decisions D17-D21
```

**Один PR — одна тема** (D29). Побічна правка, помічена по дорозі, — не в цю
гілку: сказати автору й запропонувати окрему. Виняток — документація, яку
вимагає сама зміна (нове рішення в `DECISIONS.md`), окремим комітом `docs/`.
Перед `gh pr create` перевіряти diff на сторонні зміни так само, як на секрети.

**Мова (D23):** код, коментарі, коміти, PR, issues, кореневий README —
англійською. Виняток: `docs/` і `.claude/` — українською до окремого PR
перекладу. Спілкування з автором у чаті — українською.
