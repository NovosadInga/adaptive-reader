# DECISIONS

> Важливі рішення та їхнє обґрунтування. Кожне рішення має ціну — вона вказана явно.
> Формат: рішення → чому → чим за це платимо.
> Нові рішення дописуємо в кінець. Скасовані позначаємо як Superseded, не видаляємо.

---

## D1. Головна взаємодія — переклад речення, а не словник

**Рішення.** Клік по слову або фразі показує переклад усього речення українською
з підсвіченою частиною, що відповідає виділеному.

**Чому.** Словникове значення не пояснює роль слова в конкретному реченні
(«be charged with» — не про слово «charge»). Переклад речення з підсвіткою дає і
значення, і контекст одночасно, і знімає з користувача вибір режиму допомоги.

**Ціна.** Потрібне зіставлення фрагментів оригіналу й перекладу (word alignment).
Українська та англійська мають різний порядок слів, тож позицію не порахувати
арифметично — її має повертати модель, а код мусить валідувати результат і
коректно поводитися, коли фрагмент не знайдено.

**Наслідок.** Три окремі рівні допомоги (Word / Phrase / Context) із блупринту
не потрібні — контекст вбудований у кожну підказку.

---

## D2. Автоматичне виділення — за об'єктивною складністю, не за рівнем

**Рішення.** Підсвічуються об'єктивно складні місця тексту. Рівень користувача лише
зсуває поріг, а не визначає «все вище мого рівня».

**Чому.** Для читача A1 у звичайному романі майже кожне друге слово вище його рівня.
Чесна підсвітка «всього вищого» перетворює сторінку на суцільну заливку, і виділення
втрачає сенс. Об'єктивно складних місць у будь-якому тексті мало за визначенням.

**Ціна.** Складніше визначити «об'єктивно складне» — це не одне порівняння з порогом,
а комбінація сигналів (частотність, тип конструкції, граматика).

**Наслідок.** Проблема щільності виділень зникає без лімітів і повзунків.

---

## D3. Автоматичне виділення — не блокує MVP

**Рішення.** R8 реалізується після головної взаємодії, а не разом із нею.

**Чому.** Клік по слову не потребує попереднього аналізу тексту — достатньо самого
слова та речення. Тобто головна функція продукту не залежить від найскладнішої
та найризикованішої частини системи.

**Ціна.** Перша працююча версія не має автоматичних підказок.

**Наслідок.** Найризикованіша залежність у проєкті розв'язана. Це найважливіше
рішення Phase 0.

---

## D4. Mobile-first, парсинг книги на сервері

**Рішення.** Головна платформа — телефон. Розбір файлу книги відбувається на сервері.

**Чому.** Читання книг реально відбувається з телефона. Але розбір великого файлу
у браузері телефона ненадійний: 400-сторінкова книга здатна вичерпати пам'ять вкладки.
Сервер віддає готове представлення книги, яке важить у рази менше.

**Ціна.** Варіант «фронтенд + IndexedDB + AI API» без бекенду (розділ 23 блупринту)
відпадає. Бекенд потрібен уже на першому етапі, а не в Phase 3.

**Наслідок.** Ключ від AI API природно лишається на сервері — це вимога безпеки
для публічного репозиторію (див. D8).

---

## D5. Формати: EPUB, FB2, HTML, TXT, потім PDF

**Рішення.** Підтримуємо п'ять форматів. Порядок реалізації: EPUB → FB2 → HTML → TXT → PDF.

**Чому.** PDF описує, де намалювати кожен символ, а не текст як текст — звідси
склеювання рядків, колонтитули, вгадування меж розділів. EPUB — це фактично zip із
HTML: текст уже структурований, зміст із розділами вбудований, метадані є.
EPUB, FB2 і HTML мають спільний нормалізатор розмітки, тож це майже один парсер.

**Ціна.** PDF — найпоширеніший формат у користувачів — з'явиться не одразу.

**Наслідок.** На чистому тексті помилки AI-підказок відрізняються від помилок
парсингу. На PDF ці дві причини плутаються й ускладнюють налагодження.

---

## D6. Єдине внутрішнє представлення книги

**Рішення.** Кожен формат має свій парсер, який видає одну спільну структуру
(розділи → абзаци → речення). Reader і AI працюють тільки з нею й нічого не знають
про формати.

**Чому.** Інакше кожен новий формат протікає в UI та в аналіз. Додати формат має
означати «написати парсер», а не «змінити пів застосунку».

**Ціна.** Один додатковий шар абстракції на старті.

---

## D7. Тільки файли з текстовим шаром. Без OCR

**Рішення.** Скановані PDF і DJVU не підтримуються. Такий файл відхиляється зі
зрозумілим повідомленням.

**Чому.** OCR — окремий платний сервіс або важка модель, а його помилки розпізнавання
зіпсують мовний аналіз, і причину буде важко знайти.

**Ціна.** Частину книг з інтернету завантажити не вдасться.

---

## D8. Публічний репозиторій, портфоліо-проєкт

**Рішення.** Код відкритий від початку. Секрети — тільки через змінні середовища.

**Чому.** Проєкт має бути частиною портфоліо. Ключ від AI API, випадково закомічений
у публічний репозиторій, — це не лише витік, а й реальні списані гроші; це найчастіша
помилка в подібних пет-проєктах.

**Ціна.** README, зрозуміла історія комітів і якість коду стають частиною роботи,
а не «колись потім».

---

## D9. Один користувач зараз, але стан — окрема сутність

**Рішення.** Авторизації в MVP немає. Але стан користувача (рівень, прогрес,
налаштування) від початку зберігається як окрема сутність, а не «глобальні дані».

**Чому.** Мета — у майбутньому дати читалку іншим людям. Якщо стан прив'язаний до
структури з самого початку, додати другого користувача — це зміна схеми, а не
переписування застосунку.

**Ціна.** Трохи більше структури, ніж потрібно одній людині сьогодні.

---

## D10. Публічне демо — на public domain книгах

**Рішення.** У публічному демо доступні 2–3 книги з Project Gutenberg. Завантаження
власного файлу теж працює, але завантажені книги не публікуються.

**Чому.** Демо, у якому людина одразу бачить продукт, значно цінніше для портфоліо,
ніж порожній екран із кнопкою. Водночас публічний сервіс, куди будь-хто вантажить
захищені авторським правом книги, — інша правова ситуація, ніж персональний інструмент.

**Ціна.** Треба підготувати демо-книги і зберігати їх окремо від користувацьких.

**Не вирішено.** Точні правові межі не з'ясовані. До публічного деплою це треба
перевірити окремо (див. OPEN у `CURRENT_STATE.md`).

---

## D11. Одна книга за раз

**Рішення.** У MVP немає бібліотеки: завантажив → читаєш → замінив.

**Чому.** Екран бібліотеки — це приблизно тиждень роботи, який не наближає до
критерію успіху «прочитати книгу цілком».

**Ціна.** Замінивши книгу, ти втрачаєш зручний доступ до попередньої.

**Перегляд.** Повернутися до цього після того, як буде прочитано першу книгу.

---

## D12. Читання доступне одразу, аналіз доганяє у фоні

**Рішення.** Після завантаження книга відкривається щойно розібрано текст.
Аналіз складності триває у фоні, розділ за розділом.

**Чому.** Чекати десятки хвилин перед першою сторінкою неприйнятно. Клік по слову
працює з першої секунди, бо він on-demand і аналізу не потребує (див. D3).

**Ціна.** Потрібен явний стан «аналіз триває» в інтерфейсі, і виділення не повинні
з'являтися ривками просто перед очима читача.

---

## D13. Головна ціль — портфоліо

**Рішення.** Порядок цілей у `PROJECT.md` змінено: публічний портфоліо-проєкт
на першому місці, навчання — на другому, персональний інструмент — на третьому.

**Чому.** Автор хоче показувати проєкт публічно як доказ технічної роботи.

**Ціна.** README, робоче демо й охайна історія комітів стають обов'язковою
частиною роботи, а не завершальним етапом. Завершеність важливіша за кількість
функцій — межі MVP треба тримати жорсткіше, особливо з темпом «щодня по трохи».

---

## D14. Окремий фронтенд і окремий API

**Рішення.** Два окремі проєкти замість одного суміщеного застосунку.

**Чому.** Чітке розділення відповідальності, зрозуміліше для стороннього читача коду.

**Ціна.** Два деплої, налаштування CORS, трохи повільніший старт.

---

## D15. Стек: React + Vite + TS / Node + Fastify + TS / Postgres

**Рішення.**

| Шар | Технологія |
|---|---|
| Frontend | React + Vite + TypeScript |
| Backend | Node + TypeScript + Fastify |
| База | Postgres, hosted (Neon) + ORM |
| AI | Anthropic SDK, тільки на бекенді |
| Хостинг | Railway або Render — постійний процес, не serverless |

**Чому.** TypeScript з обох боків — одна мова, менше перемикання уваги.
React обрано через головну ціль (D13). Serverless не підходить, бо фонова обробка
книги (D12) не вміщується в модель «функція виконалася і завершилась».

**Ціна.** React новий для автора — це третій новий пласт разом із серверною
розробкою та AI. Ризик не дійти до кінця зростає. Пом'якшення: пояснювати React
з основ, не ускладнювати фронтенд без потреби.

**Не вирішено.** Конкретні бібліотеки для розбору EPUB, FB2 і PDF та вибір ORM.
Визначити на першому кроці реалізації, перевіривши актуальність і ліцензії.

---

## D16. Книга зберігається документом, речення мають стабільні id

**Рішення.** Книга зберігається як структурований документ (розділи → абзаци →
речення), а не окремими рядками по реченнях. Але кожне речення отримує стабільний
ідентифікатор із самого початку.

**Чому.** Рядки по реченнях потрібні лише для аналізу складності, який свідомо
другорядний (D3) — робити важку схему заради ще неіснуючої функції передчасно.
Стабільні id при цьому не коштують нічого зараз і дозволяють прив'язати результати
аналізу пізніше без перебудови сховища.

**Ціна.** Коли аналіз з'явиться, знадобиться окрема таблиця з посиланням на id речень.
